# Claude Code スキル設計パターン — 31 個から学ぶ作り方

シリーズ: 11-documentation-plan / 関連: 06-commit-message-conventions / 08-cli-via-ai-prompts

## この文書の狙い

このリポジトリには `.claude/skills/` 配下に **31 個のスキル** がある。スキルは **「日本語のひと言で複合作業を呼び出す仕組み」** で、Claude Code を「対話相手」から「お抱えオペレーター」に変える鍵。本書ではスキルの設計パターン・命名規則・連携方法を、実例ベースで解説する。

---

## 1. スキルとは何か（一般論）

### 1-1. 実体は Markdown 1 ファイル

スキルは `.claude/skills/{name}/SKILL.md` に置かれた Markdown ファイル。Claude Code 起動時に **自動で読み込まれ**、`description` の `Triggers on "..."` を見てユーザーの発話と照合される。

ファイルの最小形:

```markdown
---
description: Use when ... Triggers on "トリガー語1", "トリガー語2".
---

# {スキル名}

{何をするか、1 段落で}

## トリガー
| ユーザーの表現 | 動作 |
| ... | ... |

## 手順
1. ...
2. ...
```

### 1-2. AI から見た「振る舞い」

ユーザーが `/コミットして` と書く（または「コミットして」と自然言語で頼む）と:

1. Claude Code がスキル一覧から `description` 一致を検索
2. `commit/SKILL.md` を全文読む
3. 手順に従って Bash / Edit / Read を実行

つまりスキルは **「LLM への動的な指示書」**。プロンプトエンジニアリングの再利用可能な単位。

### 1-3. 普通のプロンプトとの違い

| 観点 | 都度プロンプト | スキル |
|---|---|---|
| 再現性 | 毎回書く | 1 回書けば永続 |
| 共有 | 個人内 | リポジトリで共有 |
| 改善 | 毎回試行錯誤 | 蓄積される |
| 呼び出し | 長文を打つ | ひと言 |
| バージョン管理 | なし | git で履歴 |

スキル = **チームの自動化資産**。

## 2. このリポジトリの 31 スキル

### 2-1. カテゴリ別一覧

| カテゴリ | スキル | 用途 |
|---|---|---|
| **Git 系** | `commit` / `push` / `pr` | コミット・プッシュ・PR |
| **開発サーバー** | `dev-server` / `test` / `test-azure` / `docker-test` | 起動・テスト |
| **デプロイ** | `deploy-azure` | Azure デプロイ |
| **ドキュメント** | `save-report` / `devlog` / `qiita` / `zenn` | 保存・記事化 |
| **AI 機能** | `rag-search` / `narrate` | 検索・実況 |
| **コンテンツ作成** | `create-project` / `edit-blocks` / `character` / `asset` / `map` / `rpg-preview` | プロジェクト・素材 |

| **Vercel ガイド** | `vercel-react-best-practices` / `vercel-composition-patterns` / `vercel-react-native-skills` | React 規範 |
| **デザイン** | `web-design-guidelines` | UI レビュー |

### 2-2. 設計の階層

スキルは **3 層** に分かれる:

1. **アクション層**（`commit`, `push`, `dev-server`）— 既存スクリプト/コマンドを呼ぶラッパ
2. **ワークフロー層**（`create-project`, `character`）— 複数 API 呼び出しを束ねる
3. **モード層**（`narrate`）— 振る舞いを切り替える（メモリ書き換え）

## 3. 設計パターン

### パターン A: アクション層 — ラッパ

**特徴**: 既存の shell スクリプトや CLI を呼ぶだけ。

例: `dev-server` → `./scripts/dev-start.sh`

```markdown
## ルール
- **必ず `./scripts/dev-start.sh` を使う**
- 手動で `npm run dev -w ...` を個別実行しない
```

**設計意図**:
- スクリプト側で **既存プロセス停止 → DB 確認 → npm install → 起動** を完結
- スキルは「これを使え」と AI に指示するだけ
- スクリプトを直すと **スキルも自動で更新** される（DRY）

### パターン B: 一連のフローを箇条書きで指示

**特徴**: 手順を 1〜N の番号で並べ、AI に順次実行させる。

例: `commit` の手順:

```markdown
1. `git status` で変更ファイルを確認
2. `git diff --stat` で変更内容の概要を把握
3. 直近コミット（`git log --oneline -5`）を見てメッセージスタイルを確認
4. ステージするファイルを決定（下記ルール参照）
5. コミットメッセージを作成
6. `git commit` を実行
7. `git status` で成功を確認
```

**設計意図**:
- AI が **どの順で何を実行すべきか** を明示
- 手順 3「直近コミットを見る」のような **判断材料** も含める
- 各手順の出力で次の手順を変える余地（`git status` の結果でステージ決定）

### パターン C: トリガー語の網羅 — 同義語を全部書く

例:

```markdown
| "コミットして" | 全変更をステージしてコミット |
| "全部コミットして" | 同上 |
| "変更をコミットして" | 同上 |
| "ドキュメントだけコミットして" | docs/ のみステージしてコミット |
| "コードだけコミットして" | packages/ apps/ のみステージしてコミット |
```

**設計意図**:
- ユーザーが言う **可能性のある言い回しを全部列挙**
- 単純な同義語 + **修飾語による分岐**（"ドキュメントだけ" → ステージ範囲変更）
- AI は表を見て「どのトリガーに該当するか」を判断

### パターン D: 強制ルール（負のリスト）

例: `dev-server`:

```markdown
## ルール
- **必ず `./scripts/dev-start.sh` を使う**
- 手動で `npm run dev -w ...` を個別実行しない
```

**設計意図**:
- AI は何でも代替案を出してくる → **「これ以外しないで」を明示**
- `--no-verify` を使わない、`git push --force` を打たない、等の **禁止パターン** を書ける
- CLAUDE.md と連動

### パターン E: ファイル/コマンドへの直接参照

例: `broken-memo`:

```markdown
## 壊れたメモファイル
\`\`\`
docs/09_reports/2026/03/08/08-broken-items.md
\`\`\`
このファイルが存在しない場合は、同日の `docs/09_reports/` フォルダに新規作成する。
```

**設計意図**:
- **正解のパス** を 1 か所に書く
- 存在しなければ「どう作るか」も書く
- AI が迷わない

### パターン F: スキル間の連携

例: `push` の手順:

```markdown
1. `git status` で未コミットの変更がないか確認
   - 未コミットがある場合は commit スキルを先に発動するか確認する
```

**設計意図**:
- スキルは **単機能** に絞る
- 別スキルが必要なら **「commit スキルを先に」** と誘導
- 連鎖が生まれる: `/commit` → `/push` → `/deploy-azure`

### パターン G: モード切り替え（メモリ書き換え）

例: `narrate`:

```markdown
## ON にしたとき
MEMORY.md に `narrate_mode: on` を書き込む。
```

**設計意図**:
- スキルは **永続状態** をメモリに残せる
- 次回以降の Claude Code セッションでも有効
- 「実況オン」と言えば以降ずっとしゃべる

### パターン H: 自動トリガー（ユーザー入力なし）

例: `broken-memo`:

```markdown
## トリガー
テスト（ユニットテスト・E2E テスト）を実行した結果、
失敗が発生したとき**自動的に**実行する。
```

**設計意図**:
- ユーザーが指示しなくても **特定の状況** で起動
- 「テストが失敗したとき」「コミット直後」のような後続作業
- AI が自発的にスキルを呼ぶ

## 4. トリガー語の良い例 / 悪い例

### 良い例

| トリガー | 良い理由 |
|---|---|
| "コミットして" | 動詞 + ます形、意図明確 |
| "テストして" | 簡潔、対象（テスト）明示 |
| "Capacitor 却下理由を検索して" | 検索クエリが含まれている |
| "壊れたメモ更新" | プロジェクト用語 |

### 悪い例（避けるべき）

| トリガー | 悪い理由 |
|---|---|
| "やって" | 何をか不明 |
| "お願い" | 動詞も対象もない |
| "それ" | 文脈依存すぎる |
| "確認" | スキルが多すぎてどれを指すか不明 |

### 設計のコツ

- **動詞 + 目的語** で書く（例: "コミットする"）
- **プロジェクト固有の単語** を入れる（"アセット", "壊れたメモ"）
- 短すぎず長すぎず（5〜15 文字）
- 同義語を 3〜5 個用意

## 5. スキル間の連携設計

### 5-1. 連鎖の例

```
ユーザー: "実装してテスト通してプッシュして"
   ↓
Claude Code: 実装（Edit ツール群）
   ↓
/test スキル発動 → 全テスト pass 確認
   ↓
失敗時 → /broken-memo スキル自動発動
   ↓
/commit スキル発動 → Co-Authored-By + 感想付きコミット
   ↓
/push スキル発動 → リモート反映
```

### 5-2. 依存関係を「手順内」で書く

`push/SKILL.md` 抜粋:

```markdown
1. `git status` で未コミットの変更がないか確認
   - 未コミットがある場合は commit スキルを先に発動するか確認する
```

つまり「**スキルを先に**」と書くだけで、AI が他スキルを起動する。スキル定義間に **明示的なグラフ構造** は無く、**自然言語による示唆** で連結される。

### 5-3. CLAUDE.md がメタ情報を提供

`CLAUDE.md` の Rules セクション:

```markdown
### コミットは必ず commit スキル経由（必須）
git commit を直接実行しない。必ず /commit を使う。
```

CLAUDE.md は **「どのスキルを優先的に呼ぶか」** の上位ガイダンス。スキルと CLAUDE.md は **一対** で機能する。

## 6. 既存スクリプトとの層別化

このリポジトリの賢い構造:

```
スキル（指示書）          .claude/skills/dev-server/SKILL.md
   ↓ 呼び出し
シェルスクリプト（実行）  scripts/dev-start.sh
   ↓ 呼び出し
npm script              package.json
   ↓
実行ツール              vite, next, tsc, etc.
```

**スキル ≠ 実行ロジック**。スキルは AI への **指示書**、実行は既存スクリプトに任せる。

これにより:
- スクリプトの変更でスキルを直さなくて良い
- 人間も同じスクリプトを直接叩ける（AI 経由でも、手動でも）
- スキル/CLAUDE.md は「使い方」、スクリプトは「やり方」

## 7. 自分のプロジェクトへの移植手順

### Step 1: ディレクトリを作る

```
.claude/skills/{your-skill}/SKILL.md
```

または `skill.md`（小文字）でも認識される。

### Step 2: frontmatter を書く

```yaml
---
description: Use when {状況}. Triggers on "トリガー1", "トリガー2".
---
```

`description` は必須。`Triggers on` の文字列で AI が照合する。

### Step 3: 本文を書く

最小スケルトン:

```markdown
# {スキル名}

{1 段落の説明}

## トリガー
| ユーザーの表現 | 動作 |
| --- | --- |

## 手順
1. ...
2. ...

## 注意
- 禁止事項
```

### Step 4: 既存資産を呼ぶ

ロジックは **既存のスクリプト / npm script** に閉じる。スキルは「これを使え」と書くだけ:

```markdown
## ルール
必ず `./scripts/your-script.sh` を使う。
```

### Step 5: 試す

Claude Code を再起動してスキルを認識させ、トリガー語で呼んでみる。**期待通り動かなければ手順を修正** → スキルファイルを直すだけで反映。

### Step 6: 連携を加える

別スキルから呼ぶように、手順内で:

```markdown
事前に commit スキルを発動するか確認
```

これだけで連鎖が生まれる。

## 8. アンチパターン

### NG-1. 巨大スキル

500 行を超えるスキルは **AI のコンテキストを食う**。1 スキル 1 機能に絞る。

### NG-2. ロジックをスキルに直書き

```markdown
## 手順
1. JSON を読む
2. for 文で反復
3. 各要素を処理...
```

これは **コードであるべき**。スキルは「スクリプト名を指す」だけにする。

### NG-3. トリガー語が抽象的

`description: Triggers on "確認".`

「確認」だけでは AI が他のスキルと迷う。**プロジェクト固有の語** を入れる。

### NG-4. 連鎖の暴走

スキル A が B を呼び、B が C を呼び... と設計すると、AI が **意図せず連鎖を全実行** する。各スキルは **「呼び出すか確認する」** ステップを入れる。

## まとめ

- **スキル = 動的な指示書** — Markdown 1 枚でプロンプトを再利用化
- **3 階層**: アクション層 / ワークフロー層 / モード層
- **トリガー語は同義語を網羅**、動詞 + 目的語、プロジェクト固有語
- **スキル ≠ ロジック実装** — 既存スクリプトを呼ぶだけのラッパに留める
- **連携は自然言語で示唆** — 「先に commit スキルを発動」で自然に連鎖

31 スキルあるこのリポジトリの結論: **「Claude Code をオペレーターに変える」のは設計の問題で、技術の問題ではない**。 1 日でこのレベルのスキルセットは組める。
