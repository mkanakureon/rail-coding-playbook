# devlog — git log + 感想ブロックから開発日誌を自動生成

シリーズ: 11-documentation-plan / 関連: 06-commit-message-conventions / 13-skill-design-patterns

## この文書の狙い

毎日の開発を **公開ブログ的な日誌** にしたい — でも書く時間がない。本リポジトリは **`/devlog` スキル**で git の 1 日分のコミットから読み物形式の日誌を自動生成し、`docs/landing/devlog/` に蓄積している。コミットメッセージの **「Claude の一言」** が原文の感想素材になる構造を解説する。

---

## 1. devlog とは何か

### 1-1. 形式

```
docs/landing/devlog/{YYMM}/{YYYY-MM-DD}.md
```

- 1 日 1 ファイル
- Markdown
- 数百〜千数百字、3〜10 セクション
- 末尾に Claude の感想

### 1-2. 役割

- **公開**: ランディングページ（Next.js）から自動配信、訪問者が読む
- **記録**: 過去の自分が何をやったか後から辿れる
- **広報**: 「このプロジェクトは活発に動いている」を伝える
- **教材**: 開発過程の生々しい記録

## 2. このリポジトリの実装

### 2-1. スキル定義 — `.claude/skills/devlog/SKILL.md`

```markdown
---
description: ... Triggers on "開発日誌", "devlog", "日誌", "今日の振り返り".
---

## 保存先
docs/landing/devlog/{YYMM}/{YYYY-MM-DD}.md

## 素材の収集手順
1. 対象日のコミットを時系列順に取得:
   git log --since="{日付}T00:00:00" --until="{翌日}T00:00:00" --all --reverse \
       --format="%H %s"

2. 各コミットの変更統計を取得:
   git log ... --stat --format="%n--- %s ---"

3. 合計行数を取得:
   git log ... --numstat | awk '{ins+=$1; del+=$2} END {print ins, del}'

4. 必要に応じて個別コミットの diff を読む
```

### 2-2. 文章のスタイル指針（スキル抜粋）

```markdown
## 人称
あやふやにする。主語を省略し、誰がやったか明示しない。
- OK: 「取り掛かったのは〜」「追加した」「見つかった」「修正した」
- NG: 「私が〜」「開発者が〜」「Claude が〜」

## トーン
- 開発者日記っぽく、淡々と事実を語る
- 「地味だけど」「意外と」「結局」など、少し主観を混ぜる
- 変更行数やファイル数を織り交ぜて具体性を出す
```

### 2-3. 構成テンプレ

```markdown
# kaedevn開発日誌 — 2026年4月22日

> 35コミット / +8,681行 / -7,058行

## {トピック1のタイトル}

（コミット内容を読み物風に展開。変更行数・ファイル数を含める）

## {トピック2のタイトル}

...

────────────────────────────────────────────────────

（Claude Code の感想。10 行以上）

                        Claude Opus 4.7
```

ポイント:
- **コミット数 + 追加 / 削除行数** をサマリーに置く
- セクションタイトルは **コミットメッセージそのままではなく、読み物として意味のあるタイトル**
- 関連コミットは **1 セクションにまとめる**（1 commit 1 section ではない）
- 末尾に **長文の感想**

### 2-4. 感想素材の供給源

各コミットメッセージの **「Claude の一言」**（前書 06）が devlog の原文素材になる:

```
feat(hono,prisma): Phase 2 Week 5 #7 — プレイヤー状態拡張

（本文）

---
stamina の「遅延計算」設計、背景ジョブ不要でシンプルに済むのが気持ちよい。
cron で毎分 tick するより、updatedAt と interval から算出する方が
スケールも桁違いに楽。

Co-Authored-By: Claude Opus 4.7 (1M context) <noreply@anthropic.com>
```

devlog の感想ブロックには **これを統合** して書く。複数コミットの感想を読みやすく流す。

## 3. 使い方

### 3-1. 当日の生成

```
ユーザー: 「開発日誌書いて」
   ↓
/devlog スキル発動
   ↓
1. git log で当日のコミット取得
2. --stat と --numstat で変更行集計
3. 各コミットメッセージの感想ブロック抽出
4. テーマ別にグルーピング
5. docs/landing/devlog/{YYMM}/{YYYY-MM-DD}.md に書き出し
6. （オプション）コミット
```

### 3-2. 過去日付の生成

```
ユーザー: 「開発日誌書いて 2026-03-05」
```

→ 指定日のコミットから生成。後から書き直したい時に便利。

### 3-3. Next.js への反映

`docs/landing/devlog/` 配下の md は Next.js が自動でルーティング・公開（既存の dev-log ページ機能）。
**ファイルを置くだけで Web 公開される** ので、追加の手作業ゼロ。

## 4. なぜそうするか（優位性）

### 4-1. コミットメッセージが「日誌の原文」になる構造

devlog 単体で書こうとすると、コミットの意図を **思い出す作業** が発生する。

このリポジトリでは:
1. **コミット時点で感想を書く規律**（commit-msg フックで強制、前書 06）
2. その日の感想を **devlog で集約**

の二段で、**「思い出す作業」がゼロ**。コミット時の温度感がそのまま日誌に流れる。

### 4-2. 主語あやふやで書く理由

```
NG: 「私が API を実装した」
OK: 「API を実装した」「取り掛かった」
```

- **読者が誰でも違和感がない**（人間 / AI が書いたかブラされる）
- **チーム作業っぽさ**が出る
- 後から第三者が読んでも引っかからない

### 4-3. 変更行数を入れる効果

```
> 35コミット / +8,681行 / -7,058行
```

- **規模感**が伝わる
- 「ちゃんと書いてる」感
- 過去日と比較できる（毎日のばらつきが分かる）

### 4-4. セクション統合で「物語」になる

1 commit 1 section ではなく、関連を **1 トピックにまとめる**:

```
(NG)
## feat: A 機能追加
## fix: A の bug 修正
## test: A のテスト追加

(OK)
## A 機能の実装と落とし穴
（A 機能を作る → bug が見つかった → テスト追加で対応、の流れを 1 段で）
```

物語として読める文章に再構成することで、読者が **筋を追える**。

### 4-5. 感想で締める

技術的事実 → 主観の感想で締めることで、**ブログとして完結**。「淡々と事実 + 一言主観」が devlog の典型構造。

### 4-6. 日付フォルダで凍結

`docs/landing/devlog/2604/2026-04-22.md` のように **凍結された記録**。後から修正しない（直したいなら別記事）。**履歴として永続**。

## 5. 自分のプロジェクトへの移植手順

### Step 1: 保存先の規約を決める

```
docs/devlog/{YYMM}/{YYYY-MM-DD}.md
docs/blog/{YYYY}/{MM}/{YYYY-MM-DD}.md
posts/{YYYY-MM-DD}.md
```

何でも良い、1 つに決める。

### Step 2: コミット規約を整える

devlog の **質はコミットメッセージの質に依存**。前書 06 と同じく:

- プレフィックス（feat / fix / docs ...）
- Phase / Day 番号
- 本文（## セクション、テスト結果）
- **感想ブロック（`---` 区切り）**
- Co-Authored-By

を **commit-msg フックで強制**。これが devlog の原料になる。

### Step 3: スキル作成

`.claude/skills/devlog/SKILL.md`:

```markdown
---
description: ... Triggers on "開発日誌", "devlog", ...
---

## 保存先
docs/devlog/{YYMM}/{YYYY-MM-DD}.md

## 手順
1. git log --since=今日 --reverse --format="%H %s"
2. git log --stat --numstat で行数集計
3. 各コミットの本文 + 感想を取得
4. テーマ別にグルーピング
5. テンプレに従って書き出し

## スタイル
- 主語あやふや
- 行数・ファイル数を織り交ぜる
- 「地味だけど」「意外と」など少し主観を混ぜる
- セクション見出しは読み物として意味を持つ
- 末尾に感想 10 行以上
```

### Step 4: テンプレ

```markdown
# {プロジェクト名}開発日誌 — {YYYY}年{M}月{D}日

> {N}コミット / +{追加行}行 / -{削除行}行

## {トピック 1}

（読み物風）

## {トピック 2}

...

────────────────────────────────────────────────────

（感想）

                        Claude {モデル名}
```

### Step 5: 公開

- Next.js / Astro / Hugo 等で `docs/devlog/` を直接ルーティング
- または GitHub Pages
- または Markdown のまま社内 wiki

**ファイルを置くだけで公開** される構造を作る。

## 6. アンチパターン

### NG-1. コミット感想なしで devlog を書く

→ AI が「内容を推測して脚色」するため事実に対する忠実度が下がる。**コミット時に書く感想こそが原文**。

### NG-2. 主語を明示する

「私は」「開発者は」「AI は」を入れると **読者がつまずく**。あやふやが正解。

### NG-3. コミットを 1:1 でセクションにする

→ 30 コミットの日が **30 セクション** になり読めない。**統合 + 物語化**。

### NG-4. 行数・ファイル数を書かない

→ 読者が **規模感を掴めない**。`+8,681行` のような数字が信頼性を高める。

### NG-5. 感想を書かない

→ 「事実の羅列」になり読み物として弱い。**末尾に温度感のある感想** で締める。

---

## まとめ

- **devlog = git log + 感想ブロック → 読み物形式の日誌**
- 保存先は `docs/landing/devlog/{YYMM}/{YYYY-MM-DD}.md`
- 主語あやふや、行数を織り交ぜる、関連コミットを 1 セクションに統合
- **コミット時に感想を書く規律**が原文素材になる
- ファイルを置くだけで Next.js が公開

「毎日の開発が自動でストーリー化される」仕組み。**コミット規約 → スキル → 公開** の 3 段が組み合わさると、**書く時間ゼロで開発ブログが運用** できる。
