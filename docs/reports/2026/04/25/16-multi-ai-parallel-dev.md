# Multi-AI 並列開発 — Claude Code + Gemini CLI を同じリポで走らせる

シリーズ: 11-documentation-plan / 関連: 04-document-implementation-workflow / 06-commit-message-conventions

## この文書の狙い

このリポジトリは **Claude Code + Gemini CLI を並列で走らせている**。同じコードベースで 2 AI が同時に書いても衝突せず、両者の強みを活かせる **物理分離 + 役割分担** の設計を解説する。

---

## 1. なぜ Multi-AI なのか（一般論）

### 1-1. 1 AI で完結しない理由

- **得意分野が違う**: Claude は判断的 / 要約的、Gemini は網羅的 / 列挙的、Cursor はコード補完即応
- **コンテキスト窓 / 価格 / 速度のトレードオフ** がモデルごとに違う
- **障害時の冗長化**（API ダウンや quota 切れの保険）
- **同じ題目を別 AI に書かせる** ことで盲点を減らす

### 1-2. ナイーブな並列の問題

2 AI を **何も区別せず走らせる** と:
- 同名ファイルで上書き合戦
- どちらの判断か後で追えない
- コミットの著者が混乱

→ **物理分離 + 役割分担** が必要。

---

## 2. このリポジトリの設計

### 2-1. AI 別の出力先を **物理分離**

```
docs/
├── 01_in_specs/           ← 人間が書いた仕様（原典）
├── 09_reports/            ← Claude Code が生成した文書
│   └── 2026/MM/DD/NN-...md
├── 10_ai_docs/            ← Gemini CLI が生成した文書
│   └── 2026/MM/DD/NN-...md
└── landing/codebase-docs/ ← 共用（コード説明）
```

**フォルダ単位で AI を割り当てる**。同名ファイルの衝突がパス階層で起きない。

### 2-2. ガイダンスファイルの分離

| ファイル | 対象 |
|---|---|
| `CLAUDE.md` | Claude Code が読む |
| `GEMINI.md` | Gemini CLI が読む |
| `AGENTS.md`（あれば） | 他の AI 統合 |

両者は **同じプロジェクト規約を共有**するが、**書き手 AI 向けの注意** をそれぞれ含める。

### 2-3. 役割分担の例（Phase 1）

実観測:

| 文書 | 場所 | 書き手 |
|---|---|---|
| Phase 1 計画書 | `docs/09_reports/2026/04/21/01-phase1-...-plan.md` | **Claude Code** |
| Phase 1 設計書 | `docs/10_ai_docs/2026/04/21/01-...-design.md` | **Gemini CLI** |

**計画は Claude、設計は Gemini** の二者分担。各 AI の特徴と一致:
- Claude: 「目的・成果物・スケジュール・意思決定ログ」のような **判断 + 要約** が得意
- Gemini: 「アーキ図・パッケージ構成・インターフェース定義」のような **網羅 + 構造記述** が得意

両者の文書は **相互リンク** で補完する。

### 2-4. CLAUDE.md と GEMINI.md の同期

両者には共通する規約（Forbidden Patterns / Change Zones / Build Commands）があるが、書き手の癖に合わせて **若干文体を変える**:

- CLAUDE.md は手順 + 判断材料を詳しく
- GEMINI.md は全体像を先に俯瞰

両者を完全同期せず、**「同じ情報 / 違う見せ方」** を許容する。**重要な変更は両方に反映** するのがルール。

## 3. 使い方

### 3-1. 同じタスクを別 AI に渡す

```
ユーザー → Claude Code: 「Phase 2 計画書を書いて」
ユーザー → Gemini CLI:  「Phase 2 設計書を書いて」
```

Claude が `09_reports/.../plan.md` を、Gemini が `10_ai_docs/.../design.md` を書く。**並列で走る、衝突しない**。

### 3-2. クロスレビュー

```
ユーザー → Claude: 「Gemini が docs/10_ai_docs/.../design.md に書いた設計書をレビューして」
```

Claude が Gemini の設計を読んで、矛盾点・抜けを指摘 → **AI ↔ AI クロスレビュー** が成立。

### 3-3. 棲み分けのルール（実観測）

| 作業 | おすすめ AI | 理由 |
|---|---|---|
| 計画書・要約・意思決定ログ | Claude | 判断的、要点を絞る |
| 設計書・網羅的リファレンス | Gemini | 列挙が得意 |
| コードのバグ修正 | Claude | 文脈追跡力 |
| ボイラープレート生成 | Gemini | 速度 + 量 |
| 既存コードの理解 | どちらでも | コンテキスト次第 |
| デバッグ仮説の発散 | 両方並列 | 視点が違う案が出る |

絶対のルールではなく、**強みと作業のマッチング** で都度選ぶ。

## 4. なぜそうするか（優位性）

### 4-1. 並列実行で衝突しない

別 AI に同時に違う側面（実装計画 vs アーキ設計、本流 vs 反対意見）を書かせても、出力先が分離しているので **同名衝突しない**。git の merge conflict も発生しない。

### 4-2. 判断のバイアスが追跡可能

半年後に:
- 「Claude は楽観的に書きすぎる傾向がある」
- 「Gemini は冗長だが網羅性は高い」

のような **メタ評価** ができる。1 つのフォルダにごっちゃに入れるとこの分析が不可能。

### 4-3. `grep` で AI ごとに切り出せる

```bash
grep -r 'Capacitor' docs/09_reports/   # Claude の判断
grep -r 'Capacitor' docs/10_ai_docs/   # Gemini の判断
```

同じ題目に対する 2 AI の判断差分が読める。**「なぜ違うのか」を分析** できる。

### 4-4. ロールバック単位が明確

「今日 Claude が書いた一連の文書を全部消す」が:

```bash
rm -rf docs/09_reports/2026/04/25/
```

の 1 コマンドで済む。**Gemini の出力には影響しない**。AI ごとの試行錯誤が独立。

### 4-5. クロスレビュー文化

計画は Claude、設計は Gemini に書かせ、**計画書から設計書へリンクする**ことで:
- 二者の視点が必ず交差
- 1 AI で一気通貫させるより合意形成が固い
- 矛盾があれば人間がレビュー時に気づく

### 4-6. 価格・速度・コンテキスト窓のトレードオフ

実運用での選び方:

| モデル | 強み | 弱み |
|---|---|---|
| Claude Opus 4.7 (1M context) | 巨大コンテキスト + 判断力 | 単価高い |
| Claude Sonnet 4.6 | バランス、速い | コンテキスト窓は標準 |
| Gemini 2.5 Pro | 100 万トークン、安い | 判断ブレ |
| GPT-4o | コード補完 | 別 SDK |

**作業の重要度 + コンテキスト要求** で都度切り替え。

## 5. 自分のプロジェクトへの移植手順

### Step 1: AI 別フォルダを切る

```
docs/
  ai/
    claude/      ← Claude Code 用
    gemini/      ← Gemini CLI 用
    cursor/      ← Cursor 用（将来）
```

または既存命名を流用（このリポは `09_reports/` `10_ai_docs/`）。

### Step 2: ガイダンスファイル

ルートに:
- `CLAUDE.md`（Claude Code 用）
- `GEMINI.md`（Gemini CLI 用）
- `AGENTS.md`（共通、または最大公約数）

各ファイル冒頭に **「あなたが書く文書は `docs/ai/{your-name}/` に保存」** を明記。

### Step 3: 共通規約の運用ルール

- **規約変更は両方に反映** する PR を作る習慣
- どちらか一方だけ更新したらレビューで指摘
- **規約の単一情報源** を別ファイル（例: `docs/conventions.md`）にして、CLAUDE.md / GEMINI.md は **相互参照** にする手もある

### Step 4: 役割分担を試す

最初の Phase で:
- Claude に計画書
- Gemini に設計書

を頼んでみる。両者の出力を比較し、**自分のプロジェクトでの強み**を観測。

### Step 5: クロスレビューの流れ

```
1. Claude が計画書を書く
2. Gemini に「Claude の計画書をレビューして」と頼む
3. Gemini が docs/ai/gemini/.../review.md を出す
4. Claude にも逆方向でレビューさせる
5. 両者の指摘を merge して計画を確定
```

これで **AI ↔ AI ↔ 人間** の 3 者合議が成立する。

---

## 6. アンチパターン

### NG-1. AI を区別せず同じフォルダに書かせる

→ 衝突 + 後で追えない。**最低でもフォルダ分離**。

### NG-2. CLAUDE.md と GEMINI.md を完全同期させる

→ 同期コストが高い。**同じ情報 / 違う見せ方** を許容するほうが運用が楽。

### NG-3. 同じ題目を 2 AI で同時並列に書かせて統合する

→ 統合作業が重く、矛盾解消で時間ロス。**役割分担して両者で完成形** を作るほうが効率的。

### NG-4. クロスレビューを毎回やる

→ レビュー疲れ。**重要 Phase だけ** クロスレビュー、小規模はどちらか単独で OK。

---

## まとめ

- **AI 別の出力先を物理分離** — フォルダで衝突回避
- **CLAUDE.md / GEMINI.md** で書き手向けガイダンスを分ける
- **役割分担**（計画 = Claude / 設計 = Gemini）で強みを活かす
- **`grep` で AI ごとに切り出し** て判断のバイアスを分析
- **クロスレビュー** で矛盾を検出
- ロールバックは AI 単位で `rm -rf`

「AI の数は増えるが、出力は混ざらない」設計。**1 AI 依存を脱却**して、各 AI を専門員として運用する第一歩。
