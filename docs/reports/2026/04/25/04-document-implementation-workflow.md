# 第 1 部 — フォルダの役割と命名規則

## フォルダの設計思想

| フォルダ | 役割 | 書き手 | 寿命 |
|---|---|---|---|
| `docs/01_in_specs/` | **原典**（最初に書く・直さない） | 人間 | 永続 |
| `docs/09_reports/` | **作業報告・計画書・設計書・分析・完了レポート** | **Claude Code** | 日付で区切る |
| `docs/10_ai_docs/` | **作業報告・計画書・設計書・分析・完了レポート** | **Gemini CLI** | 日付で区切る |
| `docs/landing/codebase-docs/` | **コード説明書** | 共用 | コードに追従 |

設計上のキモは 2 段階:

### 段階 1: 「人間の原典」と「AI の作業ログ」の物理分離

- `01_in_specs/` は **人間が書いた仕様**。AI は読むだけ・直さない。
- `09_reports/` `10_ai_docs/` は **AI が生成した作業文書**。日付で凍結される。

### 段階 2: AI ツール別の **物理隔離**

- `09_reports/` = Claude Code が書いた成果物
- `10_ai_docs/` = Gemini CLI が書いた成果物
- **同じ機能を別 AI で並列開発**しても、同名ファイルで衝突しない
- 後で読むときに「どの AI の判断か」がパスから即判別できる
- 例: Phase 1 は Claude Code が `09_reports/2026/04/21/01-phase1-...-plan.md`、Gemini CLI が同じ機能の設計書を `10_ai_docs/2026/04/21/01-...-design.md` に置いて **計画と設計を別 AI に任せる** 形

> 補足: 過去の文書には `04_plans/`（廃止予定）など別の経緯フォルダも残るが、**新規は 09_reports（Claude Code）/ 10_ai_docs（Gemini CLI）に集約** されている。

## 命名規則（実観測）

```
docs/09_reports/{YYYY}/{MM}/{DD}/{NN}-<slug>.md
                                 ↑    ↑
                                 │    └─ 内容を表す英語スラッグ
                                 └────── その日の何件目か（01, 02, 03...）
```

例:
```
docs/09_reports/2026/04/13/
  01-3d-asset-sourcing.md
  02-vrm-support-plan.md
  03-2d-pixel-asset-sourcing.md
  04-vrm-implementation-plan.md
  05-vrm-technical-design.md
  06-vrm-implementation-postmortem.md
  07-vrm-why-it-worked.md
  08-vrm-3d-roadmap.md
  09-novel-vrm-integration-plan.md
  10-novel-vrm-integration-design.md
```

**1 日のセッションの全工程が 10 ファイルに刻まれている**。これは後述する「**書く → 作る → 振り返る**」のサイクルをそのまま物理化したもの。

## ファイル冒頭の定型ヘッダ

実観測:

```markdown
# Phase 1 計画書：KSC VM C++ 移植 + Android/iOS ストア課金

**作成日：** 2026-04-21
**対象：** Phase 1（KSC VM の Switch 共有化 + 買い切り / 消費型課金）
**関連設計書：** [docs/10_ai_docs/2026/04/21/01-ksc-vm-cpp-billing-design.md](...)
**ステータス：** Draft（ユーザー承認待ち、着手未）
```

要素:
- **作成日**（必須）— 後で読むときに「この時点の判断」と分かる
- **対象** — スコープを 1 行で
- **関連リンク** — 計画 ↔ 設計 ↔ 完了レポートが相互参照
- **ステータス** — Draft / 着手中 / 完了 / 廃案

YAML フロントマター付の例もある:

```yaml
---
generated_by: Claude Opus 4.7
date: 2026-04-19
type: plan
project: kaedevn-monorepo
---
```

# 第 2 部 — 標準ワークフロー

このリポジトリの実観測から導かれる **「タスクの粒度別ワークフロー」**。

## A. 大規模機能（Phase 単位 = 1〜2 週間）

例: **Phase 1（KSC VM C++ 移植 + 課金）**, **Phase 2（運営型ソシャゲ）**, **VRM 実装**

このリポジトリの基本パターンは **「設計 → 計画 → 実装 → テスト」**。ふつう「計画」と「設計」を逆順に書く現場が多いが、ここでは **何を作るか（設計）が先、どう積むか（計画）が後**。理由は後述。

```
┌─ 0. 仕様（docs/01_in_specs/）           — 人間の原典として既に存在
│
├─ 1. 比較・採算・実現可能性調査          — 09_reports に多数併走
│   ├─ 01-g123-mementomori-feasibility.md
│   ├─ 02-oss-strategy.md
│   ├─ 04-platform-economics.md
│   ├─ 16-3d-background-feasibility.md
│   ├─ 18-3d-engine-selection.md
│   └─ ... 20 ファイル
│
├─ 2. 設計書（design）                     — 10_ai_docs/.../01-...-design.md（Gemini CLI）
│   ├─ アーキテクチャ図 / システム構成
│   ├─ パッケージ構成
│   ├─ インターフェース定義（IBilling 等）
│   ├─ データフロー
│   └─ 「何を作るか・どう繋ぐか」を確定
│
├─ 3. 計画書（plan）                       — 09_reports/.../01-phase1-...-plan.md（Claude Code）
│   ├─ 目的・非ゴール
│   ├─ 成果物リスト（D1〜D11）— 設計書の構成要素を成果物に展開
│   ├─ 意思決定ログ（採用案 vs 却下案）
│   ├─ スケジュール（日割り Day 1〜Day 14）
│   ├─ 完了基準
│   └─ 設計書への相互リンク
│
│   （設計は Gemini、計画は Claude と分担して二者の視点を交差させる運用）
│
├─ 4. 実装                                 — git commit 履歴
│   ├─ Day 1: 骨格作成
│   ├─ Day 2: 算術 opcode
│   └─ Day N: 統合
│   各 commit のメッセージに Co-Authored-By + 感想（pre-commit で強制）
│
├─ 5. テスト                               — vitest, ktest, parity
│   ├─ ユニット: 83 ケース
│   ├─ Parity: 4 fixtures bit-exact
│   └─ Integration: 5 ケース
│
└─ 6. 完了レポート（completion）           — 09_reports/.../02-...-completion-report.md
    ├─ 結論（達成 / 未達）
    ├─ 成果物一覧（コミットへのリンク）
    ├─ テスト結果
    ├─ コード規模
    └─ 残タスク（環境依存などフェーズ外）
```

### なぜ「設計 → 計画」の順なのか

普通のプロジェクト管理書は「計画（タスク・スケジュール）→ 設計（具体）」と教える。このリポジトリは逆で、**設計が先**。理由は AI 時代に特化した実利:

1. **設計が固まらないと成果物リストが書けない** — Phase 1 の成果物 D1〜D11 は **設計書のパッケージ構成を 1:1 に成果物化** したもの。設計が無いと計画書の D が量産できない
2. **スケジュール見積もりは設計を見ないと当てずっぽうになる** — opcode 数・テーブル数・関数数を設計書で確定してから「Day N に何個やる」が決まる
3. **計画段階でコケない** — ふつうの計画 → 設計だと、計画通りに着手して設計を書いた瞬間に「あ、無理」となる。設計を先にやって実装可能性を確かめてから日割りに落とす
4. **AI がスケジュールを読みやすい** — 計画書から「設計のあの章を見ろ」と参照できる

実観測の効果:
- **Phase 1 完了レポート**は「14 コミットで 14 日分の成果物」「全 83 + 5 テスト pass」と機械的に書ける。**設計書の構成 → 計画書の D 成果物 → commit が 1:1:1** で対応しているため
- **意思決定ログ**（採用案 vs 却下案）が後から読めるため、半年後に「なぜ Capacitor を選ばなかったか」を再議論せずに済む

## B. 中規模機能（数日〜1 週間）

例: **VRM 実装（1 セッション）**, **インタプリタ文法拡張**

```
1. 設計（design）        — 05-vrm-technical-design.md
   ├─ アーキテクチャ概観
   ├─ システム構成（VN エンジン ↔ 3D フィールド）
   └─ Phase A〜F の技術的中身（モデル読込 / トゥーン / 表情 / SpringBone）
2. 計画（plan）          — 04-vrm-implementation-plan.md
   ├─ 設計書の Phase A〜F を時系列タスクに展開
   ├─ なぜ先行実装するかの背景
   └─ 完了基準
3. 実装                  — git commit 単位で Phase A → B → C → D → E
4. テスト・動作確認        — `prototypes/vrm-test/index.html` で目視
5. ふりかえり（postmortem） — 06-vrm-implementation-postmortem.md
   ├─ つまずいたポイントと真因
   ├─ 仮の見立てが何度ハズレたか
   └─ 修正の経緯（再現可能な記述）
6. 「なぜすんなり進んだか」分析 — 07-vrm-why-it-worked.md
   ├─ 寄与の内訳（glTF 30% / 下準備 40% / 場数 30%）
   └─ 次に活かす成功要因
7. 統合計画                  — 09-novel-vrm-integration-plan.md
   └─ ノベル機能との合流（再び設計 → 計画の順で）
```

> 注: VRM の場合、ファイル番号 04（plan）→ 05（design）の順だが、これは作成順ではなく **検索性のため計画書を先頭に並べる便宜**。実際のセッション中の作成順は `05-technical-design.md`（何を作るか確定）→ `04-implementation-plan.md`（Phase A〜F に分解）。設計書冒頭の「ステータス: 設計確定（実装前）」と計画書冒頭の「関連: 05-vrm-technical-design.md（設計書）」の相互参照がそれを示す。

実観測の効果:
- **postmortem に「仮の見立て 1 → ハズレ → 仮の見立て 2 → ハズレ → 真因」を全部書く**。次に同じ層（Filament の WASM バインディング等）に触る人（or AI）が、迷う段階をスキップできる。
- **「なぜ成功したか」を分解して書く**ことで、次の機能（Live2D / 3D マップ）に成功要因を意図的に再現できる。

## C. 小規模リファクタ（数時間〜半日）

例: **`Value` 型の切り出し**, **インタプリタ文法拡張**

小規模では **設計と計画を 1 文書に統合**する。「方針」セクションが設計、「対象表」セクションが計画、という形:

```
1. 計画書 1 枚（設計 + 計画統合、薄め）  — 02-value-type-refactor-plan.md
   ├─ 背景・目的
   ├─ 方針（= 軽い設計：型定義・インターフェース）
   ├─ 置換対象表（= 計画：どのファイルをどう直すか）
   ├─ 非ゴール（やらないこと）
   └─ 完了基準
2. 実装 → コミット 1 つ
3. テスト pass 確認
4. （省略可）結果ノート
```

設計が単純な場合（型定義の追加など）に分離するコストの方が高い。**規模に応じて分けるか統合するかを判断**するのもこのリポジトリの実用性。

特徴: **「直接コードを書きにいかず、まず計画書を 50〜100 行書く」**。これが当リポジトリで最も再現価値の高い習慣。

理由（実観測から）:
- 「やらないこと」を明文化することで、AI が暴走しない（「ついで」にリファクタを広げない）
- 「置換対象表」が型エラーを誘導するチェックリストになる
- 計画書時点でユーザーが Draft レビューできる → 着手後の手戻りゼロ

## D. 計画 → 結果のペア構造

例: **ランディング更新**

```
docs/09_reports/2026/04/20/
  01-landing-update-plan.md      ← 計画
  02-landing-update-result.md    ← 結果（実装後）
```

**同じ日の連番で「計画 → 結果」を必ずペアにする**。後から見たときに、計画通り行ったか・ズレたかが 2 ファイルの diff で読める。

# 第 3 部 — 実装中の規律（CLAUDE.md と連動）

文書ワークフローは、CLAUDE.md の Rules と密に連動している。

## 実装着手前

1. **RAG 検索（習慣）** — `docs/` を MCP の `search_docs` で検索 or `Grep`（CLAUDE.md「作業前の RAG 検索」）
2. **計画書 Draft** を `09_reports/今日/NN-...md` に書く（ユーザー承認待ち）
3. **C ゾーン変更がある場合**は Design Change Note も Draft に含める

## 実装中

1. **コミット粒度**: 1 機能 = 1 commit（実観測: Phase 1 は Day = commit）
2. **コミットメッセージ**: `/commit` スキル経由必須（pre-commit で `Co-Authored-By` と感想区切り `---` を強制）
3. **`@xxx` 追加時の 8 箇所追従**: command-sync テストが落ちて気付ける（CLAUDE.md「Adding New Script Commands」）
4. **C ゾーン変更時**: コミットメッセージか docs に Design Change Note 必須（pre-push で blocked）

## 実装後

1. **テスト pass 確認** — vitest / ktest / E2E の該当箇所
2. **動作確認** — UI 変更なら playwright + browser-verify、API 変更なら curl
3. **完了レポート / postmortem** を `09_reports/今日/NN-...md` に書く
4. **計画書から相互リンク** を貼る（前述の三点リンク構造）

# 第 4 部 — このワークフローの優位性（理由付き）

「なんとなく良い」ではなく、**実観測の事象に対する原因分析**として優位性を 8 つ挙げる。

## 0. 「設計 → 計画 → 実装 → テスト」順の効果

### 観測

このリポジトリでは **設計書を計画書より先に確定** させる:

- Phase 1: `10_ai_docs/2026/04/21/01-...-design.md`（Gemini）→ `09_reports/2026/04/21/01-...-plan.md`（Claude）
- VRM: `05-vrm-technical-design.md`（設計確定）→ `04-vrm-implementation-plan.md`（Phase A〜F に分解）
- 計画書の成果物 D1〜D11 は、設計書のパッケージ構成を **1:1 で展開**したもの

### 優位性

「設計を先にやる」だけだが、4 つの実利が出ている:

1. **見積もり精度が劇的に上がる** — opcode 数・テーブル数を設計で確定してから「Day N に何個」が出せる。設計を飛ばすとスケジュールがファンタジーになる
2. **計画段階のコケが消える** — 計画 → 設計の順だと「計画通り着手 → 設計を書いた瞬間に無理と判明 → 計画引き直し」が頻発する。順序を逆にすると **計画書はもう実現可能なものしか書かれない**
3. **AI が両方を参照できる** — 計画書から「設計のあの章」へリンクできる。逆順だと設計書が計画書を参照するが、それは「できあがったあとの解説」になりがち
4. **完了レポートが機械的に書ける** — 設計（構造）→ 計画（D1〜D11）→ commit（実装）→ テスト の **1:1:1:1 マッピング**ができ、「達成 / 未達」の判定が客観的になる

> ふつうの「計画 → 設計」順は、人間の感覚として「先に動こう」が強いが、AI 時代には **設計の精度がそのまま AI の実装精度** になる。設計書という静的ドキュメントを最初に固めるほうが、AI に渡せる情報量が圧倒的に増える。

## 1. 計画書の「Draft → 承認」プロセスで AI の暴走を止められる

### 観測

- Phase 1 計画書は **「ステータス：Draft（ユーザー承認待ち）」** と冒頭に明示
- 「非ゴール」「やらないこと」「却下案」を明確に書く
- 着手は承認後

### 優位性

AI（特に LLM）は「ついでに」関連箇所を直そうとする。計画書時点で **境界を文書化** することで:

- スコープ外の改変が起きても、レビュアーが「計画書にない変更」と即指摘できる
- AI 自身が「やらないこと」を読み返せる（コンテキストに常駐させる）
- ユーザーが Draft 段階でフィードバックできる → コードを書いた後の **手戻り削減**

> 効果の実例: Phase 1 完了レポートで「コード面の目標を全て達成」と機械的に書けたのは、計画書の成果物 D1〜D11 と commit が 1:1 マッピングされたから。

## 2. 「意思決定ログ」が将来の議論コストを削る

### 観測

```markdown
| 日付 | 決定 | 採用案 | 却下案 |
|------|------|--------|--------|
| 2026-04-21 | 配信方式 | SDL2 ネイティブ | Capacitor・React Native |
| 2026-04-21 | KSC 実行方式 | ルート A: C++ 手移植 | ルート B: Op 追加 |
| 2026-04-21 | VM 移植方法 | 手移植（2週、可読性優先） | TS→C++ トランスパイラ（4週）|
```

### 優位性

半年後・1 年後に同じ議論が再燃したとき、`grep -r 'Capacitor' docs/09_reports/` で **却下理由が即座に出る**。

ふつうの開発では「なぜ Capacitor を選ばなかったか」の議事録が散逸し、再議論で 2 時間溶ける。**意思決定ログを採用案/却下案ペアで書く**ことで、これをゼロにできる。

## 3. 「postmortem に仮の見立て全部」を書く効果

### 観測（VRM postmortem）

```markdown
**症状:** 14 expression のうち 4 種だけ動作
**仮の見立て 1:** Filament WASM の setMorphWeights が 4ch しか受け付けない
**仮の見立て 2:** バインディングを叩き直して配列を渡すルートを探す → 配列を受け付けることが判明
**仮の見立て 3:** 視覚に変化がない → MorphTargetBuffer の問題
**真因:** sparse 形式の morph accessor が Filament WASM gltfio で読まれない
```

### 優位性

「真因」だけ書くと、**次に同じ層に触る AI が「すでに 3 つの仮説を試した」事実を知らない**。Claude/Cursor の AI は postmortem を読んで:

- 「仮の見立て 1〜3 はもう試した。`setMorphWeights` 系・MorphTargetBuffer 系は深掘りしない」と判断
- 「真因 = sparse / dense 形式の差」をデフォルト仮説にできる

これで **デバッグの試行回数が 1/3 になる**（実観測: VRM 統合の 2 回目セッションは Filament 罠を全部スキップ）。

## 4. 「なぜ成功したか」分析でレベルを意図的に再現できる

### 観測（07-vrm-why-it-worked.md）

```markdown
| 寄与 | 内訳 |
|---|---|
| glTF ベースだったこと | 30% |
| 下準備（プロトタイプ + 設計書 + 良い素材 + 即確認できる環境） | 40% |
| トラブル対処の場数で押し切った部分 | 30% |
```

### 優位性

ふつうの開発は「成功した」で終わる。**何が効いたかの内訳分析** をすると:

- 次の機能（Live2D・3D マップ）で **同じ下準備を意図的にやる** ようになる
- 「下準備 40%」が再現可能なノウハウとして文書化される
- AI も「過去成功時の構造」を読み取って真似できる

> 実観測: VRM 後の 3D マップ作業で、`docs/09_reports/2026/04/13/08-vrm-3d-roadmap.md` のような **次への計画書** が即座に出ている。これは「下準備 40%」のパターン化。

## 5. 「日付フォルダで凍結」の心理効果

### 観測

`docs/09_reports/2026/04/21/` の中身は **2026-04-21 に書いたまま**。ファイル名やパスが変わらない。

### 優位性

- **「直さない」が物理的に保証される**ため、過去の判断を後付けで修正する誘惑が消える
- リンクが永続的（`../../../../09_reports/2026/04/21/01-...md` のような相対パスが切れない）
- **git log と並列読み**ができる（コミットの日付と reports のフォルダ日付が一致）

## 6. 仕様書（人間原典）と作業ログ（AI 生成）の **物理分離**

### 観測

```
docs/01_in_specs/00_old/         ← 人間が書いた仕様書（記録）
docs/01_in_specs/2026/04/18/...  ← 人間の個別仕様
docs/09_reports/2026/04/12/      ← Claude Code が同じ時期に出した調査・採算・選定 20 件
docs/10_ai_docs/2026/04/21/...   ← Gemini CLI が出した設計書
```

### 優位性

- **「これは人間の原典か、AI の作業判断か」が paths から即判別できる**
- AI が `01_in_specs` を読むときは「これは決まり事」と扱い、`09_reports` / `10_ai_docs` を読むときは「これは過去の AI の判断」と扱える
- 古い仕様書は `00_old/` に隔離され、新規実装に紛れ込まない

## 6-bis. AI ツール別の **物理隔離**（09_reports vs 10_ai_docs）

### 観測

- `09_reports/` = Claude Code が生成した文書
- `10_ai_docs/` = Gemini CLI が生成した文書
- Phase 1 は両者を **計画 / 設計** のように **分担** で組み合わせている

### 優位性

1. **並列実行で衝突しない** — 別 AI に同時に違う側面（実装計画 vs アーキ設計、本流 vs 反対意見）を書かせても、出力先が分離しているので同名衝突しない
2. **判断のバイアスが追跡可能** — 半年後に「Claude は楽観的に書きすぎる傾向」「Gemini は冗長」のような **メタ評価** ができる。1 つのフォルダにごっちゃに入れるとこの分析が不可能
3. **`grep` で AI ごとに切り出せる** — `grep -r 'Capacitor' docs/09_reports/` と `grep -r 'Capacitor' docs/10_ai_docs/` で、同じ題目に対する 2 AI の判断差分を読める
4. **ロールバック単位が明確** — 「今日 Claude が書いた一連の文書を全部消す」みたいな操作が `docs/09_reports/2026/04/25/` の rm 一発でできる
5. **クロスレビュー文化** — 計画は Claude、設計は Gemini に書かせ、計画書から設計書へリンクすることで **二者の視点が必ず交差**する。1 AI で一気通貫させるより合意形成が固い

> 補足: この分離は「AI ツールごとに性質が違う」前提に立っている。Claude Opus は判断的・要約的、Gemini CLI は網羅的・列挙的、のような **得意分野の差** を文書出力にも反映させたいときに効く。

## 7. CLAUDE.md と文書フォルダの相互参照

### 観測

CLAUDE.md の Rules:
- 「作業前の RAG 検索」 → `docs/` を検索
- 「Adding New Script Commands」 → 8 箇所と sync テスト
- 「Change Zones」 → C ゾーンに Design Change Note

文書側からの逆参照:
- 計画書冒頭で「**関連:** CLAUDE.md / Change Zones / Forbidden Patterns / Script Command 追加手順」を列挙

### 優位性

- AI / 人間の両方が、**「規約 → 実装手順 → 文書テンプレ」を 1 経路で辿れる**
- 規約変更時は CLAUDE.md を直すだけで全文書テンプレに波及（中央集権）
- 文書を書く側も「規約のここを参照しろ」と書ける

# 第 5 部 — 真似する側へのチェックリスト

別リポジトリで同じワークフローを再現するときの最低限:

- [ ] `docs/01_specs/`（**人間の原典**）と AI 生成文書フォルダを **物理分離**
- [ ] **AI ツールごとに保存先を分ける**（例: `docs/claude/` `docs/gemini/` / `docs/cursor/` 等）
- [ ] 命名規則を `YYYY/MM/DD/NN-<slug>.md` で固定（`README.md` に書く）
- [ ] 文書冒頭ヘッダ（**作成日 / 書き手（AI 名） / 対象 / ステータス / 関連リンク**）を必須化
- [ ] 大規模機能は **設計 → 計画 → 実装 → テスト → 完了レポート → postmortem** の順（**設計が先**）
- [ ] **設計と計画を別 AI に書かせる**（設計 = Gemini、計画 = Claude のようにクロスレビュー）
- [ ] 計画書には必ず **意思決定ログ（採用案 vs 却下案）** を含める
- [ ] postmortem では **「仮の見立て全部」と「真因」** を分けて書く
- [ ] 成功時には **「なぜ成功したか」内訳分析** を必ず書く
- [ ] 計画 → 結果のペアは **同じ日の 01 / 02 連番** で
- [ ] CLAUDE.md / GEMINI.md（or AGENTS.md）から各 AI の文書フォルダへリンク、文書側から逆リンク
- [ ] **直さないフォルダ（仕様）と凍結フォルダ（日付）を分けるルール**を README.md に書く

# 結論

このリポジトリの強みは「TS のガードレール」だけではなく、**「文書が実装と同じ重さで管理されている」** こと。

- **設計を先に固める**（計画はその後）
- **計画書を書いてから実装する**（即実装しない）
- **意思決定を記録する**（採用案だけでなく却下案も）
- **テストで完了基準を満たす**（テストがないものは未完）
- **失敗を残す**（postmortem に仮の見立て全部）
- **成功を分解する**（「なぜ成功したか」の内訳）
- **日付で凍結する**（直さない）
- **AI ツール別に保存先を分ける**（Claude Code = `09_reports/`、Gemini CLI = `10_ai_docs/`）

要するに **「設計 → 計画 → 実装 → テスト」の 4 段順守 + 各段で AI のバイアスをクロスチェック + 全段を日付で凍結**。これが当リポジトリの繰り返し成功している型。

AI で実装する時代は、**コードを書く速度** よりも **判断を再現できる構造** が品質を決める。このリポジトリは、その構造を `docs/` の物理レイアウト（人間の原典 / Claude / Gemini の三分割）と CLAUDE.md の Rules で実装している。

そして第 1〜3 報で書いた **TS のガードレール（型・hooks・CI・sync テスト）** は、この文書ワークフローを「人間と AI の合意」が壊れないように **機械的に守る** 仕組み。両者は **同じ哲学の表裏**: 「**変えてよいものと変えてはいけないものを物理的に分ける**」。
