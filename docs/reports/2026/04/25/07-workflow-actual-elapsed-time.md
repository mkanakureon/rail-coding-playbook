# 標準ワークフローの実所要時間 — git コミット履歴からの実測

親文書: [04-document-implementation-workflow.md](./04-document-implementation-workflow.md) 第 2 部「標準ワークフロー」  
データソース: `git log` の実コミット間隔から算出した所要時間

## この文書の目的

親文書では「大規模 = 1〜2 週間」「中規模 = 数日〜1 週間」「小規模 = 数時間〜半日」と書いた。これは **計画書の見積もり** ベース。実際の git コミット履歴から **実所要時間** を計測すると、AI（Claude Code）と良い構造（設計 → 計画 → 実装 → テスト + ガードレール）の組み合わせで **見積もりの 1/10〜1/100** に収まっている。

実測値を残しておくことで、**「次の Phase をどれくらいで見積もるか」「AI 時代の見積もり感覚」** の参照点になる。

> 個別コミットの作業時刻は意図的に省略し、**所要時間（duration）** のみを残す。

# 総まとめ — 見積もりと実態のギャップ

| ワークフロー | 計画見積もり | 実測 | 比率 |
|---|---|---|---|
| Phase 1（KSC VM + 課金） | 14 営業日 (~110h) | **4h09m**（連続） | **~1/27** |
| Phase 2 単発 4 項目 | 4 週間相当 | **21 分** | **~1/450** |
| VRM 実装（〜表情完全動作） | 〜1 セッション | **7h02m** | 計画通り |
| VRM 統合 + 補強 | — | **+2h20m** | — |
| VRM エディタ統合 | — | **4h53m** | — |
| インタプリタ文法拡張 | 半日 | **30〜60 分** | **~1/8** |
| ランディング更新 | — | **45 分** | — |

## 倍率がスケールする要因

1. **抽象が既に固まっている**（Phase 1 → Phase 2 で 1/450 になる主因）
2. **計画書を前日に寝かせた**（インタプリタ文法拡張）
3. **設計書が成果物 D1〜Dn と 1:1 対応**（Phase 1 の 26 コミット）
4. **ガードレール（型 + hooks + sync テスト）が誤りを即時検出**
5. **コミット粒度が細かく、各コミットが pass 確認された緑状態**

## 倍率が出ない要因（VRM 系で観測）

1. **ライブラリの罠**（Filament WASM の sparse morph accessor）
2. **ブラックボックスのデバッグ**（unlit 法線が 0、bone 更新が動かない、等）
3. **「真因に当たるまでの仮説試行」**（postmortem に 3 案残るのが典型）

これは **TS の型 + 自前コードでは検出できない領域**。だから第 03 報の「TS の限界」「dist 起動テスト」「postmortem の仮説保持」が補う。

## 結論

**「設計 → 計画 → 実装 → テスト」の 4 段順守 + ガードレール + AI（Claude Code）** の組み合わせは、計画見積もりに対して:

- 抽象が新規 → **概ね 1/10 〜 1/30**
- 抽象が既に存在 → **1/100 〜 1/500**

の速度で動く。**計画書の見積もりは「もし AI なしでやったら」の上限値**として読み、実装は淡々と進める運用が現実的。

「14 営業日」の計画書を書いて 4 時間で終わらせると、**残り時間で次の Phase の設計書を書ける**。これが Phase 1 完了直後に Phase 2 計画書ドラフトが上がっている実観測の理由。
