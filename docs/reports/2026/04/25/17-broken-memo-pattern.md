# broken-memo パターン — テスト失敗とデバッグの WIP メモを集約する

シリーズ: 11-documentation-plan / 関連: 09-all-tests-overview / 13-skill-design-patterns

## この文書の狙い

テストが失敗したとき、原因を即特定できないことがある。**「複数の仮説を試しながら原因を絞る」過程を記録する場所**として、このリポジトリは `broken-items.md` という WIP メモを使い、**`/broken-memo` スキルで自動更新**している。本書はそのパターンを解説する。

---

## 1. broken-memo とは何か

### 1-1. 役割

`docs/09_reports/{date}/NN-broken-items.md` というファイルに、現在進行中のデバッグ案件を集約:

- どのテストが失敗しているか
- どの仮説を試したか / ハズレたか
- どの仮説が **真因** だったか
- 修正が完了したらステータスを更新

これは **postmortem の WIP 版** + **デバッグ作業の足場**。

### 1-2. postmortem との違い

| | broken-memo | postmortem |
|---|---|---|
| 寿命 | WIP 中（数時間〜数日） | 完了後の記録（永続） |
| 形式 | 仮説併記、ステータス遷移 | 真因 + 教訓 |
| 更新 | 何度も書き換える | 1 回書いたら触らない |
| 配置 | `09_reports/.../*-broken-items.md` | `09_reports/.../*-postmortem.md` |
| 目的 | **次の検証ステップを決める** | **次に同じ罠にハマらない** |

WIP の途中経過 → broken-memo、確定したら postmortem。

## 2. このリポジトリの実装

### 2-1. スキル定義 — `.claude/skills/broken-memo/SKILL.md`

```markdown
---
description: Use when tests fail and the broken-items memo needs updating.
             Auto-triggers after test failures.
             Also triggers on "壊れたメモ更新", "broken memo".
---

## トリガー
テスト（ユニットテスト・E2E テスト）を実行した結果、
失敗が発生したとき**自動的に**実行する。
ユーザーから「壊れたメモ更新して」「broken memo 更新」等の明示指示でも実行する。
```

ポイント:
- **自動トリガー**: テスト失敗時に Claude Code が自発的にスキルを起動
- **明示トリガー**: 人間が「壊れたメモ更新して」と言っても起動

### 2-2. ステータス遷移

| ステータス | 意味 | 表記 |
|---|---|---|
| 新規記録 | 失敗を発見、未着手 | ❌ |
| 調査中 | 原因を調査中 | 🔍 |
| 修正済み | 原因特定・修正完了 | ✅ |

ファイル内のサマリー表でアイコンを切り替えて状態を一望。

### 2-3. 実例 — VRM ブロックの壊れたメモ

`docs/09_reports/2026/04/18/01-vrm-block-broken-items.md` の構造（実観測）:

```markdown
# VRM ブロック — 壊れたメモ

## 検証結果サマリー

| 項目 | 状態 | 概要 |
|------|------|------|
| VRM ブロック追加・編集・削除 | ✅ | E2E テスト 4/4 passed |
| プレビュー：スクリプト生成（原因 A/B/C） | ✅ | 修正済み |
| プレビュー：VRM 増殖（原因 D） | ✅ | entity 削除 + 同一モデルスキップで修正済み |

## 1. VRM プレビュー — スクリプト生成の不具合（原因 A/B/C） — 修正済み

### 根本原因（3つ）と修正内容

#### 原因 A: スクリプト生成が key=value 形式だったが ...
**修正**: useEditorStore.ts で pos=center → pos center に変更。

#### 原因 B: VrmRenderer.setTransform が加算的で累積していた
**修正**: basePosX/basePosY/baseScale を applyPos() で保持。

#### 原因 C: ピクセル→3D空間の変換比率が未検証だった
**修正**: カメラ設定から pxToUnit = 1.2/1280 を算出。

## 2. VRM プレビュー — snapshot 送り直しで VRM が増殖する（原因 D）— ✅ 修正済み

### 症状
エディタでブロックを選択し直すたびに、プレビュー iframe に snapshot が再送信される。
そのたびに前の VRM が残ったまま新しい VRM が追加され、画面上に VRM が増殖する。

### ブラウザ検証結果
| テスト | 結果 |
| 初回 @vrmShow hero | ✅ VRM 1体が正しく表示 |
| 2回目 @vrmShow hero x 200 | ❌ VRM 2体が表示 |
| 3回目 @vrmShow hero x 500 s 2 | ❌ VRM 3体が表示 |

### 真因
（割愛）

### 修正
（割愛）
```

ポイント:
- **複数の原因（A / B / C / D）** を併記
- 各原因に **症状 / 仮説 / 修正** を書く
- 修正済みになったら **タイトルに「— 修正済み」** を追加

## 3. 使い方

### 3-1. テスト失敗時（自動）

```
ユーザー: 「テストして」 → /test スキル起動
   ↓
テスト実行 → 失敗あり
   ↓
/broken-memo スキル自動起動
   ↓
docs/09_reports/{今日}/NN-broken-items.md に追記 or 新規作成
   ↓
ユーザー: 「修正して」
   ↓
Claude Code が壊れたメモを参照 → 仮説を立てて修正試行
   ↓
修正成功 → broken-memo のステータスを ❌ → ✅ に更新
   ↓
コミット
```

### 3-2. 明示更新

```
「壊れたメモ更新して」
「broken memo 更新」
```

→ 現在のテスト失敗を再集計、メモに反映。

### 3-3. 別セッションでの再開

数日後の別セッションで:

```
ユーザー: 「VRM 関連の壊れたメモを見て、続きをやって」
   ↓
Claude Code が docs/09_reports/.../vrm-block-broken-items.md を Read
   ↓
「原因 A/B/C は修正済み、原因 D が残ってる」と把握
   ↓
原因 D に絞って作業継続
```

**メモを読めば即座にコンテキスト復元** できる。

## 4. なぜそうするか（優位性）

### 4-1. 複数仮説を併記する効果

ふつうのデバッグログは **真因だけ** を残しがち:

```
「sparse morph accessor が原因だった」
```

しかし broken-memo は:

```
仮の見立て 1: setMorphWeights が 4ch 制限 → ハズレ
仮の見立て 2: バインディング配列対応 → 通った
仮の見立て 3: MorphTargetBuffer 問題 → 部分的に当たり
真因: sparse 形式 + WASM 制約
```

**ハズレた仮説を残す** ことで、次に似た症状に当たった時に「これはもう試した」と即除外できる。**デバッグの試行回数が 1/3 に**。

### 4-2. 自動トリガーで「忘れない」

テスト失敗を見つけたら **修正前に必ず記録**。スキルが自動起動するので人間が忘れる余地がない。

### 4-3. ステータス遷移でレビュー可能

```
| 項目 | 状態 |
|------|------|
| A | ✅ |
| B | 🔍 |
| C | ❌ |
```

サマリー表を見れば **「何が片付いて何が残っているか」が 1 秒で分かる**。

### 4-4. 別セッション・別 AI でも引き継げる

メモは Markdown ファイルなので:
- 別の Claude Code セッションで Read
- Gemini CLI に「これを参考に続きを」
- 別の人間がレビュー

**WIP 状態のシリアライズ** として機能する。

### 4-5. 修正完了後に postmortem に昇格

broken-memo が「全て ✅」になったら、内容を編集して postmortem として `06-vrm-implementation-postmortem.md` のようなファイルに昇格させる。WIP → 完了文書 の自然な流れ。

## 5. 自分のプロジェクトへの移植手順

### Step 1: ディレクトリ規約を決める

- `docs/09_reports/{YYYY/MM/DD}/NN-broken-items.md`（このリポ流）
- または `docs/wip/broken-items-{topic}.md`（topic 別）
- または GitHub Issues + ラベル「wip」

ファイルパス規約を 1 つ決める。

### Step 2: テンプレ作成

```markdown
# {トピック} — 壊れたメモ

## 検証結果サマリー

| 項目 | 状態 | 概要 |
|------|------|------|

## 1. {問題タイトル}

### 症状
（再現条件・観測した現象）

### 仮の見立て 1: ...
（試した内容と結果）

### 仮の見立て 2: ...

### 真因（特定後に追記）

### 修正
（修正前にここを書かない、修正後に書く）
```

### Step 3: スキル作成

`.claude/skills/broken-memo/SKILL.md` を作成:

```markdown
---
description: Use when tests fail. Auto-triggers after failures.
---

## 手順
1. テスト失敗内容を抽出
2. 該当 broken-memo ファイルを Read
3. なければ新規作成
4. 失敗を ❌ で記録
5. 修正済みなら ✅ に変更
```

### Step 4: テストスキルから呼ぶ

`/test` スキル末尾に:

```markdown
## 失敗時
失敗があった場合は /broken-memo スキルを発動して記録する。
```

これで連鎖が成立。

### Step 5: ステータスアイコンの統一

❌ / 🔍 / ✅ をプロジェクト全体で統一。grep で「未解決」を集計可能:

```bash
grep -rn "❌" docs/09_reports/ | wc -l
```

## 6. アンチパターン

### NG-1. 真因だけ書く

仮説を残さないと **次に同じ症状で詰まる**。「ハズレた仮説」も価値ある情報。

### NG-2. 修正前に「修正方法」を書く

```
### 真因: x が null だった
### 修正: ?? チェックを追加
```

→ 仮説段階で確定的に書くと **嘘の記録** になる。**確定後に追記** する規律。

### NG-3. ファイル名がトピックを表さない

`broken-items.md` だけだと **何のメモか不明**。`vrm-block-broken-items.md` のように **トピックを名前に含める**。

### NG-4. 修正後に削除する

→ 教訓が失われる。**「— 修正済み」を追記して残す**。後でリポジトリ全体を grep して同種の問題に再利用できる。

---

## まとめ

- **broken-memo = WIP デバッグの足場 + 仮説併記** のパターン
- ファイル: `docs/09_reports/{date}/NN-{topic}-broken-items.md`
- ステータス: ❌ / 🔍 / ✅
- 自動トリガー（テスト失敗時）+ 明示トリガー
- **仮説を全部残す** ことで次回のデバッグが速くなる
- 完了したら **postmortem に昇格** する自然な流れ

「複数の仮説を試して真因に辿り着く」プロセスを **ファイルにシリアライズ** することで、AI も人間も **WIP の続きから再開** できる。これがデバッグの組織記憶。
