## 1. 目的と背景

### 1.1 ゴール

`docs/09_reports/2026/04/25/01〜09` で **「AI 連携の基盤と思想」** を記述したが、**個別の実装テクニック（MCP / スキル / フック / AI Metadata API 等）** は未カバー。これを **「IT 経験者が読むと実装できる」** 粒度で追加文書化する。

最終的な体裁:

```
docs/09_reports/2026/04/25/
├── 01-09 (既存・基盤シリーズ)
└── 11-N (追加・実装テクニックシリーズ)  ← 本計画の範囲
```

完成イメージ: **AI 連携リファレンス本** として読める 15〜20 文書のセット。

### 1.2 非ゴール（やらないこと）

| 項目 | 理由 |
|---|---|
| 既存文書 01〜09 の書き直し | スコープ外、別計画で扱う |
| `docs/landing/codebase-docs/` への展開 | 同上、確定後に検討 |
| Qiita / Zenn 投稿用記事化 | `/qiita` `/zenn` skill で別途、文書化が先 |
| 英語化 | 日本語完成後に検討 |
| 各文書のスクショ / 図表挿入 | テキストのみで成立する範囲に絞る（必要なら追加コミットで） |
| Gemini CLI 用文書（10_ai_docs/） | 本計画は Claude Code 用（09_reports/）のみ |

### 1.3 想定読者

- **IT 経験者だが生成 AI 開発は初心者** — TypeScript / API / 認証の基礎は分かるが、Claude Code / MCP / RAG / スキル運用は未踏
- 自分のプロジェクトに **AI 連携を真剣に組み込みたい** 人
- このリポジトリを **OSS の参考実装** として参照する人

## 3. 意思決定ログ

| 決定 | 採用案 | 却下案 | 理由 |
|---|---|---|---|
| 文書数 | 14 文書（D1〜D14） | 38 文書全部独立 | 38 は維持コスト過大、論理的に統合可能 |
| 保存先 | `docs/09_reports/2026/04/25/` 連番 | `docs/landing/codebase-docs/` | 09_reports は Claude Code 用、新規はこちら（feedback メモ準拠） |
| 番号 | 12 から連番 | 別フォルダ | 既存 01〜10 の続きで読みやすい |
| 順序 | 設計 → 計画 → 実装 → テストの 4 段順守 | 直接実装に入る | 文書 04 の規範どおり |
| 作成主体 | Claude Code 単独 | Claude + Gemini 分担 | 候補リスト（10）は Claude が書いた。整合性のため同一 AI で完成 |
| 1 文書あたり目安 | 200〜500 行 | 1000 行超大文書 | 読み切れる粒度を維持。長すぎる場合は分割 |
| サンプルコード | 抜粋（10〜30 行）| 全文掲載 | 抜粋 + ファイルパスで参照すれば十分、長文は文書を圧迫 |
| 動作確認 | 文書記載のコマンドが実機で通ること | 全コマンド実行検証 | 既存実装の解説なのでコード自体は緑。コマンド例の typo チェックのみ |
| 完了レポート | 全 D 完了後に 1 件 | 各 D ごとに完了レポート | 細かすぎる。Phase 単位で 1 件で十分 |
| ステータス管理 | 本計画書に進捗チェック表 | 別ファイルで Issue 管理 | 計画書で十分、外部ツール不要 |

## 6. 文書テンプレート（共通）

各 D は以下のスケルトンに従う:

```markdown
# {主題}

シリーズ: 11-documentation-plan / 関連: {既存文書番号}

## この文書の狙い

（200 字以内、初心者にも読める導入）

## 1. {主題} とは何か（一般論）

（業界共通の前提知識）

## 2. このリポジトリでの実装

（実体: ファイルパス + コード抜粋 + 設計判断）

## 3. 使い方

（コマンド・API 呼び出し・トリガーの実例）

## 4. なぜそうするか（優位性）

（実観測の事象から原因分析）

## 5. 自分のプロジェクトへの移植手順

（再現に必要な最小セット）

## まとめ

（要点 3〜5 行）
```

このテンプレに揃えることで:
- 読者が **どの文書も同じ章立てで読める**
- 書く側も **章ごとに穴埋め** できて速い
- AI が後から **横断比較** しやすい

## 7. リスクと対応

| リスク | 影響 | 対応 |
|---|---|---|
| 文書間で同じ説明が重複 | 読者が混乱 | 索引（D14）で「ここは X 文書を見ろ」と振る |
| コード抜粋が陳腐化（リファクタで） | 文書の信頼性低下 | 「実装は変わるが思想は残る」前提で書く。詳細はパスで参照 |
| 「IT 経験者向け」と「初心者向け」のバランス | 読みづらい | 各章冒頭に【一行で言うと】を置き、初心者は要約だけで通せる |
| 14 文書を書く途中で疲れる | 品質ばらつき | 章立てテンプレで穴埋め化、Day 単位で commit |
| 既存実装と乖離した内容を書く | 嘘文書になる | Read で原典を確認してから書く |
